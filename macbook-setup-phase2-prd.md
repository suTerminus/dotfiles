# PRD Addendum: Phase 2 — Personal & Work Overlays, Secrets, Claude Code Plugins

**Owner:** Berkay
**Status:** Draft v2
**Parent doc:** `macbook-setup-prd.md`
**Sibling docs:** `macbook-setup-discovery-prd.md`, `macbook-setup-phase0-prd.md`, `macbook-setup-phase1-prd.md`, `macbook-setup-phase3-prd.md`
**Goal:** Layer the personal and work dotfiles overlays, Bitwarden-driven secret rendering, AWS profiles, the personal Claude plugin install, and the work-org marketplace registration on top of Phase 1's public baseline. The personal overlay always applies; the work overlay applies only when `machine == "work"`.

---

## 1. Phase Boundary

Phase 2 picks up where Phase 1 left off. By the time Phase 2 begins, the new MacBook already has the public dotfiles applied, mise installed, public repos cloned, and the public Brewfile pipeline rendering correctly. What's missing is everything that depends on private inventory or secrets — that's Phase 2's job.

| | State |
|---|---|
| **Entry condition** | Phase 1 doctor (for its scope) is green. `chezmoi apply` against the public source has no diff. `~/code/personal/dotfiles` is the chezmoi source dir. The SSH key generated by Phase 0 step P0-40 (`~/.ssh/id_ed25519`) is registered with GitHub and reachable. `gh auth status` reports authenticated. The public repo inventory has been processed and `~/.config/brew/Brewfile` is rendered + bundled. |
| **Exit condition** | The personal dotfiles overlay is cloned, applied, and idempotent. **If `machine == "work"`**, the work overlay is also cloned and applied on top of the personal overlay. Bitwarden is unlocked for the run; templated config files (AWS, SSH, API keys) are rendered with values pulled from the vault. The personal Brewfile has been rendered and bundled; on work machines the work Brewfile is also rendered and bundled. Overlay-source repo inventories have been cloned, including the personal Claude plugin (from the personal overlay) and work-org repos (from the work overlay, work machines only). The personal Claude plugin is installed, and the work-org marketplace is registered as a Claude Code marketplace. A smoke-test plugin skill invocation succeeds. |

**Why Phase 2 is its own phase:** Phase 1 has no access to anything in the overlays — not the personal or work overlay inventory files, not the Bitwarden vault, not the personal or work Brewfile contents. Splitting Phase 2 off means Phase 1 can run end-to-end on a personal machine that never touches work credentials, and means a teammate cloning the public repo gets exactly the public-baseline behavior. Phase 2 is also where the only network-dependent secrets workflow lives, so its failure modes (Bitwarden auth, missing items in vault, expired SSO) are isolated from the rest of bootstrap.

Phase 2 also handles the conditional work layer: a strictly-personal machine never clones the work overlay, never sees work SSO profiles, and never installs work-only Brewfile entries. A work machine layers the work overlay on top of personal, so personal AWS profiles still land first and work-specific config is layered over them.

The Claude Code wiring in particular *cannot* happen earlier: the personal Claude plugin lives in the personal overlay's inventory and the work-org marketplace lives in the work overlay's inventory, so Phase 1 doesn't even know they exist. Registering them with Claude Code requires running plugin/marketplace commands whose syntax may have evolved — Phase 2 is responsible for verifying that against current docs at execution time. See §8.

## 2. Phase 2 Scope

### In scope

- **Bitwarden CLI unlock** — login if needed, unlock, persist `BW_SESSION` for the rest of the run, clean up at end.
- **Personal overlay clone + apply (always-on)** — the personal overlay repo is cloned to `~/.local/share/chezmoi-private` and `chezmoi apply` runs against it as a second source. Conflicts resolve in favor of personal (because it applies second).
- **Work overlay clone + apply (conditional on `machine == "work"`)** — the work overlay repo is cloned to `~/.local/share/chezmoi-<work>` and `chezmoi apply` runs against it as a third source. Conflicts resolve in favor of the work overlay (because it applies last). On personal machines this step is skipped entirely — neither the clone nor the apply runs, and the work source dir does not exist.
- **Bitwarden-templated config files** — chezmoi's `bitwarden` template function renders SSH config, AWS SSO config, AWS credentials (where needed), API keys (Anthropic, etc.) and any other secret-bearing files declared in either overlay's `home/` tree.
- **Overlay Brewfiles** — the personal overlay's `inventory/brew-personal.yaml` is rendered to `~/.config/brew/Brewfile.personal` and bundled; on work machines the work overlay's `inventory/brew-<work>.yaml` is rendered to `~/.config/brew/Brewfile.<work>` and bundled. Both use the same `scripts/render-brewfile.sh` introduced in Phase 1. Personal-machine bootstrap bundles only the personal Brewfile.
- **Overlay-source repo auto-clone** — `inventory/repos-personal.yaml` (always) and the work overlay's `inventory/repos-<work>.yaml` (work only) are read after their respective overlays are applied, and missing repos are cloned. The personal list includes the personal Claude plugin. The work list includes the work-org marketplace and other work-org repos — these previously sat in the public `repos.yaml` and have been moved to the work overlay's inventory.
- **Application Support snapshots** — chezmoi entries capture Raycast config files. v1 ships these in the personal overlay.
- **Plugin install + marketplace registration** — personal Claude plugin installed; work-org marketplace registered. Both verified with a smoke-test skill invocation. On personal machines, only the personal-plugin install runs; marketplace registration is skipped because the marketplace repo is not cloned.
- **Secrets documentation** — per-overlay `docs/secrets.md` is the canonical manifest of every Bitwarden item used by templates. Phase 2 produces and maintains them. See §7.

### Out of scope (deferred to later phases)

- **macOS defaults** — Phase 3 (`defaults write` per `inventory/macos-defaults.yaml`).
- **Touch ID for sudo** — Phase 3 (`/etc/pam.d/sudo_local`).
- **Manual-install detection** — Phase 3 (`scripts/steps/P3-20-manual-check.sh`).
- **Post-install hooks** — Phase 3 (gh extensions, app first-run config, etc.).
- **Doctor script (full)** — Phase 3 owns the full multi-phase doctor; Phase 2 ships only its own probes.
- **GPG keys** — deferred indefinitely. Q-PARENT-4 resolved in favor of SSH commit signing, which reuses the Phase 0 SSH key. There is no GPG step.
- **ghost-bazaar public/private split** — Q-PARENT-5, Future Work.
- **Additional Application Support apps beyond Raycast** — Q-PARENT-6 resolved for v1; more apps can be added later as an additive change.

## 3. Why three repos and what wins on conflict

Migrated from parent §2 verbatim and condensed for this PRD. Phase 2 is the phase that *operationalizes* the three-repo composition, so the rationale is repeated here.

### Three repos, composed at apply time

**Public dotfiles repo.** Base layer. Non-sensitive configuration: shell, editor, git basics, public CLI tool configs, and the bootstrap scripts themselves. Safe to open-source.

**Personal overlay (private).** Personal-sensitive overlay: personal AWS profiles, personal SSH hosts, personal Brewfile entries (e.g., 1Password with license refs), Application Support snapshots for apps holding personal state (Raycast license), Bitwarden-rendered API keys.

**Work overlay (private).** Work-org-specific overlay: work AWS SSO profiles, work-only Brewfile entries (Slack, work chat, corporate VPN client), work-org repo references (formerly in public `repos.yaml`), work-org tool configs. Anything that ties the machine to the employer lives here, not in the personal overlay.

All three are managed by **chezmoi**. The public repo is applied first; personal and work overlays are applied on top in order, so later overlays win on conflicts.

### Overlay rules per machine

The `machine` chezmoi prompt drives which overlays apply:

| `machine` value | Overlays applied | Order |
|---|---|---|
| `personal` | public + personal overlay | public → personal |
| `work` | public + personal overlay + work overlay | public → personal → work |

Personal-sensitive content (1Password, personal AWS) lives on both machine types because the user is the same person; work-sensitive content (corporate VPN, work SSO) only lands on work machines.

A teammate cloning only the public repo gets a working public-dotfiles setup with no expectation of access to either overlay.

### Why three repos and not two

- The public repo can genuinely stay public — no risk of leaking via a misconfigured template.
- The personal/work split lets each have its own access control, history, and rotation cadence. The work overlay can be granted to a coworker for fleet-style standardisation without exposing personal secrets.
- Putting work-only content (Slack, work chat, work AWS) in the work overlay keeps the personal overlay usable on a strictly-personal machine that should never get work tooling.
- Anyone can clone the public dotfiles to bootstrap a similar setup without needing access to either overlay.

### What "wins on conflict" actually means

chezmoi's source dir for the public repo is `~/code/personal/dotfiles` (per the Phase 1 decision). Each overlay has its own source dir, separate from the public one and from each other:

- `~/.local/share/chezmoi-private` — personal overlay source.
- `~/.local/share/chezmoi-<work>` — work overlay source (work machines only).

Phase 2's overlay model is mechanical: after `chezmoi apply` runs against the public source and succeeds (Phase 1), a second `chezmoi apply` runs against the personal source (P2-10), and on work machines a third `chezmoi apply` runs against the work source (P2-12). Files written by a later apply overwrite anything earlier applies wrote to the same destination. There is no automatic three-way merge — last-writer-wins. The apply order is **public → personal → work**, so on a work machine a work SSO profile defined in the work overlay overrides anything the personal overlay or public repo wrote at the same path.

This means a personal-on-work-machine still gets the personal overlay applied first (e.g., personal AWS profiles land), and then the work overlay layers work-specific config on top (e.g., adds work AWS profiles, work SSH hosts). Personal config is not displaced by work config — it's *augmented* by it.

The convention is therefore: **never put a non-template duplicate in an overlay if the layer below is correct.** Each overlay only contains files that either (a) don't exist in the layers below, or (b) deliberately override them. Anything else is drift.

## 4. Overlay Repo Layouts

Migrated from parent §3 (overlay trees) with notes added for Phase 2. There are now two overlay repos, each structured similarly.

### Personal overlay: `suTerminus/dotfiles-private`

```
dotfiles-private/
├── .chezmoiroot                    # contains "home"
├── .chezmoi.toml.tmpl              # inherits prompts from public init
├── README.md
├── home/
│   ├── private_dot_ssh/
│   │   └── config.tmpl             # personal SSH hosts only; references ~/.ssh/id_ed25519
│   ├── private_dot_config/
│   │   ├── aws/
│   │   │   ├── config.tmpl         # personal SSO profiles
│   │   │   └── credentials.tmpl    # rendered from Bitwarden if needed
│   │   └── raycast/
│   │       └── ...                 # Raycast config snapshot (license may be in Bitwarden)
│   ├── dot_config/
│   │   └── brew/
│   │       └── Brewfile.personal.tmpl   # rendered from inventory/brew-personal.yaml
│   └── ...
├── inventory/
│   ├── brew-personal.yaml
│   └── repos-personal.yaml
└── docs/
    └── secrets.md                  # which Bitwarden items are referenced where (personal)
```

### Work overlay (private repo)

```
dotfiles-<work>/
├── .chezmoiroot                    # contains "home"
├── .chezmoi.toml.tmpl              # inherits prompts from public init
├── README.md
├── home/
│   ├── private_dot_ssh/
│   │   └── config.tmpl             # work SSH hosts (bastion etc.)
│   ├── private_dot_config/
│   │   ├── aws/
│   │   │   └── config.tmpl         # WORK SSO profiles overlay (layered atop personal)
│   │   └── <work>/
│   │       └── ...                 # work-specific tool configs
│   ├── dot_config/
│   │   └── brew/
│   │       └── Brewfile.<work>.tmpl    # rendered from inventory/brew-<work>.yaml
│   └── ...
├── inventory/
│   ├── brew-<work>.yaml
│   └── repos-<work>.yaml
└── docs/
    └── secrets.md                  # which Bitwarden items are referenced where (work)
```

A few notes specific to Phase 2:

- **`private_*` filename prefix.** chezmoi's `private_*` prefix is honored at apply time: target files are written with mode `0600`. Used for everything under `~/.ssh/` and `~/.config/aws/` and any other paths where group/world readability would be a problem. This is the v1 perms guarantee — see §14 success criteria. Both overlays use this prefix.
- **Overlay order is strict.** Phase 2 step P2-10 applies the personal repo *after* the public `chezmoi apply` from Phase 1 succeeded. P2-12 applies the work repo *after* P2-10, on work machines only. Running them out of order produces files with wrong perms (private files end up world-readable because chezmoi's default mode applied first), which is exactly the failure mode parent §9 calls out.
- **SSH config is overlaid via templating.** Both overlays write to `~/.ssh/config`. On a work machine the work overlay applies last, so `~/.ssh/config` ends up reflecting whatever the work `config.tmpl` produces. To preserve personal hosts on a work machine, the work `config.tmpl` includes/repeats the personal-host entries (the simplest model: each overlay owns the full file it writes). An alternative — using `Include` directives so each overlay writes a separate fragment file — is rejected for v1 in favor of the simpler "last writer wins, full file" model. v1 keeps each overlay's `config.tmpl` self-contained.
- **Brewfile templates live in their respective overlays.** Public ships `home/dot_config/brew/Brewfile.tmpl`, the personal overlay ships `home/dot_config/brew/Brewfile.personal.tmpl`, and the work overlay ships `home/dot_config/brew/Brewfile.<work>.tmpl`. The `home/dot_config/brew/` directory is therefore *contributed to by all three repos*. Final paths after apply: `~/.config/brew/Brewfile`, `~/.config/brew/Brewfile.personal`, and (work only) `~/.config/brew/Brewfile.<work>`.
- **Private key file is never managed by chezmoi.** The actual `id_ed25519` private key lives only on disk and only in the user's possession — generated by Phase 0 P0-40, never committed, never rendered from a template. The only thing chezmoi-managed under `~/.ssh/` is `config` and (optionally) `known_hosts`. Public key is fine to commit if useful, but isn't required.

## 5. Step Specifications

Each step is its own script under `scripts/steps/` in the public dotfiles repo. Each is independently runnable. Each is idempotent. Each declares its idempotency probe at the top as a comment. Format mirrors Phase 0 PRD §5: **Probe / Behavior / Notes**.

### P2-00 bitwarden-unlock

**Probe:** `bw status` returns JSON whose `.status` field is `unlocked`.

**Behavior:**
- If probe passes: `skip`.
- If `bw status` reports `unauthenticated`: run `bw login` (interactive — user enters email + master password + 2FA code as configured). On success, fall through to unlock.
- If `bw status` reports `locked`: run `bw unlock --raw`, capture the session token to stdout, write it to `~/.local/state/macbook-setup/bw-session` with mode `0600`. Subsequent steps source this file to populate `BW_SESSION`.
- Register a cleanup hook (trap on `EXIT`/`SIGINT`/`SIGTERM` in the orchestrator, plus an absolute timeout): unlink `~/.local/state/macbook-setup/bw-session` at end of run, or after one hour, whichever comes first. The timeout is a defense-in-depth measure for the case where the orchestrator dies without firing the trap.

**Notes:**
- Re-running Phase 2 after the session expired re-unlocks. This is acceptable friction (parent §7 calls this out explicitly).
- `bw login` is the only step in Phase 2 that may open a 2FA prompt; everything downstream just sources the session.
- Bitwarden CLI itself is installed in Phase 1 as part of the public Brewfile (it lives in `inventory/brew.yaml`, not in private inventory). Phase 2 assumes the binary is on `$PATH`.
- The session file path matches parent §7 so doctor scripts can find it.

### P2-10 personal-overlay

**Probe:** `~/.local/share/chezmoi-private/.git` exists AND `chezmoi --source ~/.local/share/chezmoi-private diff` returns empty (no pending changes to apply).

**Behavior:**
- If `~/.local/share/chezmoi-private` does not exist: `git clone git@github.com:suTerminus/dotfiles-private.git ~/.local/share/chezmoi-private`. SSH clone uses the Phase 0 key.
- If the directory exists but is not a git repo: hard error with a clear message (refuse to overwrite).
- Run `chezmoi apply --source ~/.local/share/chezmoi-private` so the personal overlay is applied on top of the public source.
- Verify via `chezmoi --source ~/.local/share/chezmoi-private diff` that the overlay is clean.

**Notes:**
- **Always runs.** Both `personal` and `work` machines apply the personal overlay; it's the universal user layer. Only the work overlay (P2-12) is conditional.
- **Order matters.** Phase 1's `chezmoi apply` against the public source must have completed cleanly before this step runs. The Phase 2 orchestrator's preflight check confirms this; running P2-10 manually without the order guarantee produces incorrect file perms (parent §9).
- The personal source dir is *not* under `~/code/personal/` — it's `~/.local/share/chezmoi-private`. Editing the personal repo is done in `~/.local/share/chezmoi-private` directly (or in a separate clone), pushed, then `chezmoi update --source ~/.local/share/chezmoi-private` to re-apply. This mirrors the convention parent §6 documents for the public repo.
- This step depends on P2-00 having run, because the chezmoi templates in the personal overlay reference `bitwardenFields` and similar functions. If `BW_SESSION` is not set, those functions error out and apply fails partway. The orchestrator threads `BW_SESSION` through.

### P2-12 work-overlay

**Probe:** `machine == "work"` AND `~/.local/share/chezmoi-<work>/.git` exists AND `chezmoi --source ~/.local/share/chezmoi-<work> diff` returns empty (no pending changes to apply).

**Behavior:**
- If `machine != "work"`: skip entirely. Do not clone, do not apply, do not verify the directory's existence beyond confirming it should *not* exist (a leftover work source dir on a personal machine is reported by the doctor as drift — see §14).
- If probe passes: `skip`.
- Else: if the work source dir does not exist, `git clone <work-overlay-url> ~/.local/share/chezmoi-<work>`. SSH clone uses the Phase 0 key.
- If the directory exists but is not a git repo: hard error (refuse to overwrite).
- Run `chezmoi apply --source ~/.local/share/chezmoi-<work>` so the work overlay is applied on top of the personal overlay.
- Verify via `chezmoi --source ~/.local/share/chezmoi-<work> diff` that the overlay is clean.

**Notes:**
- **Order matters even more here.** P2-12 must run *after* P2-10 so the work overlay layers on top of the personal overlay (e.g., personal AWS profiles land first; work SSO profiles are added on top, sharing the same `~/.config/aws/config` file). The Phase 2 orchestrator preflight confirms P2-10 completed cleanly before P2-12 runs.
- A personal-machine user never runs P2-12. The work repo is never cloned and the work source dir does not exist. Re-running Phase 2 on a personal machine should always show this step as `skip (machine=personal)`.
- This step depends on P2-00 (Bitwarden session) for the same reason as P2-10: work templates may reference `bitwardenFields` for work-specific secrets (work API keys, work AWS account IDs, etc.).
- If a user later switches a personal machine to work-machine (changes the chezmoi prompt), re-running Phase 2 picks up P2-12 on that re-run and clones the work overlay then. There's no "demote" path for the reverse direction (work → personal) in v1; manually deleting the work source dir and re-applying is required to reverse course.

### P2-20 brew-bundle-overlays

**Probe:**
- `~/.config/brew/Brewfile.personal` exists AND `brew bundle check --file=~/.config/brew/Brewfile.personal` exits 0.
- If `machine == "work"`: also `~/.config/brew/Brewfile.<work>` exists AND `brew bundle check --file=~/.config/brew/Brewfile.<work>` exits 0.

**Behavior:**
- If probe passes: `skip`.
- Determine machine type from chezmoi's data (`chezmoi data | jq -r '.chezmoi.machine'` or whatever the convention is per Phase 1).
- **Personal Brewfile (always):** render via `scripts/render-brewfile.sh ~/.local/share/chezmoi-private/inventory/brew-personal.yaml ~/.config/brew/Brewfile.personal`. Bundle: `brew bundle install --file=~/.config/brew/Brewfile.personal`.
- **work Brewfile (work only):** render via `scripts/render-brewfile.sh ~/.local/share/chezmoi-<work>/inventory/brew-<work>.yaml ~/.config/brew/Brewfile.<work>`. Bundle: `brew bundle install --file=~/.config/brew/Brewfile.<work>`.
- Re-check probe; fail loudly if a package failed to install.

**Notes:**
- Personal machines bundle one Brewfile (personal); work machines bundle two (personal + work-org). There is no "single-Brewfile-per-machine" mode anymore — the personal layer is universal. Work-only entries (Slack, work chat, corporate VPN client) are in the work Brewfile and never appear on personal machines.
- **MAS auth pre-check.** If a rendered Brewfile contains `mas` lines, the script confirms the user is signed into the App Store first via `mas account` before running `brew bundle install`. If not signed in, log a warning, write a clear error, and skip just the MAS portion (continue with cask + formula installs). MAS sign-in cannot be automated from CLI (parent §10 question 3). The pre-check runs once per Brewfile; both personal and work Brewfiles can contain MAS entries.
- The `tags` filtering from inventory (`optional`, etc.) is honored at render time. The Brewfile that lands on disk is already filtered; `brew bundle` itself doesn't see tag metadata.

### P2-30 clone-overlay-repos

**Probe:** For each repo in `~/.local/share/chezmoi-private/inventory/repos-personal.yaml` (always), and (if `machine == "work"`) each repo in `~/.local/share/chezmoi-<work>/inventory/repos-<work>.yaml`: the target `path` exists AND `git -C <path> remote get-url origin` matches the inventory `url`.

**Behavior:**
- If every entry's probe passes: `skip`.
- Else: read `repos-personal.yaml` (always), and `repos-<work>.yaml` (if `machine == "work"`); expand `path`, check tags, skip optional-tagged entries that aren't explicitly opted in, and clone any missing entries.
- This step clones `ghost-bazaar` to `~/code/personal/ghost-bazaar` from `repos-personal.yaml`. On work machines it also clones the work-org marketplace, the work-org docs repo, the work-org postgresql repo, etc., from `repos-<work>.yaml` — see §6 inventory schema.

**Notes:**
- SSH cloning depends on the key generated by Phase 0 step P0-40. If `gh auth status` reports the key isn't registered, this step fails fast with a pointer back to P0-40.
- Behavior is the model parent §6 documents (auto-clone, idempotent, optional pull-on-update). Phase 2 doesn't introduce new repo-clone semantics — it just reads two overlay-source inventory files instead of one.
- **The work-org repos are now Phase 2's responsibility.** They previously sat in the public `repos.yaml` and were cloned by Phase 1; with the new three-repo model they live in `repos-<work>.yaml` and are cloned here. Phase 1 no longer clones any work-org repos. See §8 "Phase 1 vs Phase 2 boundary" for the full rationale.
- The merge between `repos.yaml` (cloned by Phase 1), `repos-personal.yaml` (cloned here), and `repos-<work>.yaml` (cloned here, work only) is *additive*. There is no concept of "overlay overrides public" for repo entries; an entry with the same `name` in any two files is an authoring error and the script flags it.

### P2-40 plugin-and-marketplace

**Probe:**
- `claude` lists `ghost-bazaar` as an installed plugin AND a smoke-test ghost-bazaar skill invocation returns success.
- If `machine == "work"`: also the work-org marketplace is registered as a marketplace AND a smoke-test plugin from it is reachable.

**Behavior:**
- If probe passes: `skip`.
- Else: **verify current Claude Code plugin/marketplace install commands against latest docs at execution time** (use the `find-docs` skill or `ctx7` per global rules). Do not rely on commands as documented in this PRD or the parent — see §8 implementation note.
- Read ghost-bazaar's manifest (location in repo determined by current Claude Code conventions; likely `.claude-plugin/plugin.json` or similar). If structure doesn't match current expectations, adapt the manifest before installing.
- Run the install command for `ghost-bazaar` from `~/code/personal/ghost-bazaar` (cloned by P2-30 from the personal overlay's `repos-personal.yaml`).
- If `machine == "work"`: run the marketplace registration command for the work-org marketplace from `~/code/<work-org>/claude-marketplace` (cloned by P2-30 from the work overlay's `repos-<work>.yaml` — *not* by Phase 1).
- Smoke test: invoke a known ghost-bazaar skill (e.g., a stub `hello-skill` or one of the actual personal skills) and confirm Claude Code recognizes and runs it. The exact smoke-test command lives in `ghost-bazaar/docs/smoke-test.md` so it can evolve without churn here. On work machines, also smoke-test a plugin from the work-org marketplace.

**Notes:**
- This step intentionally does not pin command syntax. See §8 "Implementation note" for the rationale, which is preserved verbatim from parent §8.
- If the smoke test fails but install + registration succeeded, the step exits non-zero with a clear message: "plugin installed but smoke-test failed; check ghost-bazaar manifest." Don't auto-rollback; the user inspects manually.
- On personal machines, only the `ghost-bazaar` install + smoke-test run; marketplace registration is skipped because `~/code/<work-org>/claude-marketplace` doesn't exist.
- This is the only Phase 2 step whose commands are fully delegated to runtime doc-check. Every other step is fully specified.

## 6. Inventory Schema (Overlays)

Phase 2 reads up to four overlay inventory files: two from the personal overlay (always) and two from the work overlay (work only). Schemas mirror the public versions (parent §5) and are reproduced here so the file is self-contained for Phase 2 implementation. Entries are *populated* during Discovery review (see `macbook-setup-discovery-prd.md` §7); the schemas here document the structure those entries fit into.

### Personal overlay (`dotfiles-private/inventory/`)

Always read by Phase 2 regardless of machine type.

#### `inventory/brew-personal.yaml`

Personal apps. Includes things present on every machine the user owns — personal password manager, music, personal media tooling.

```yaml
formulae:
  - name: ffmpeg

casks:
  - name: 1password
  - name: discord
  - name: spotify
  - name: visual-studio-code
    # Already in public Brewfile; if duplicated here, render-brewfile.sh
    # de-duplicates on (name, kind) — see Phase 1 spec.

mas:
  - id: 1Password 7 - Password Manager
    appid: "1333542190"
```

#### `inventory/repos-personal.yaml`

Renamed from earlier `repos-private.yaml` for symmetry with the work overlay's `repos-<work>.yaml`.

```yaml
# Personal-overlay repos. Same schema as public repos.yaml. Merged in at clone time.

repos:
  - name: ghost-bazaar
    url: github.com/suTerminus/ghost-bazaar
    path: ~/code/personal/ghost-bazaar
    tags: [claude, plugin]
    # Personal Claude Code plugin/skills/commands.
    # Installed via Claude Code's plugin system in Phase 2 step P2-40.
    # See section 8 (Claude Code Configuration & Plugins).

  # Add other personal repos here. Examples might include:
  #   - vault (Obsidian)
  #   - personal notes / docs repos
```

### work overlay (`<work-overlay>/inventory/`)

Read by Phase 2 only when `machine == "work"`. On personal machines, neither file is read; the repo isn't cloned.

#### `inventory/brew-<work>.yaml`

Renamed from earlier `brew-work.yaml`. Contains *only* work-specific apps — the personal layer below already provides the universal apps.

```yaml
formulae: []

casks:
  - name: slack
  - name: microsoft-teams
  - name: <corp-vpn-client>       # corporate VPN
  - name: zoom                      # if work-mandated; otherwise can move to personal

mas: []
```

#### `inventory/repos-<work>.yaml`

New file. Contains the work-specific repos that previously appeared in the public `repos.yaml`.

```yaml
# work-overlay repos. Same schema as public repos.yaml. Merged in at clone time.

repos:
  - name: claude-marketplace
    url: github.com/<work-org>/claude-marketplace

The Discovery PRD's reference to `brew-work.yaml` predates the rename to `brew-<work>.yaml`; treat them as equivalent.

## 7. Secrets Handling

Migrated from parent §7 with Phase-2-specific additions.

### Principles

- **Nothing sensitive in the public repo.** Ever. Including comments. The public repo passes a grep audit (see §14): grepping for `apikey`, `secret`, `token`, `password`, plus the user's known-secret patterns, returns zero hits. This is checked as a final pre-merge audit on every PR to the public dotfiles repo.
- **Templates over scripts.** Use chezmoi's `bitwardenFields` and `bitwardenAttachment` template functions instead of shelling out to `bw get`. Template-based rendering keeps secret pulling declarative, integrates with `chezmoi diff`, and means missing items surface as clear template errors rather than silent empty strings.
- **Document what's referenced.** the personal overlay's `docs/secrets.md` lists every Bitwarden item used by templates in the personal overlay; the work overlay's `docs/secrets.md` does the same for the work overlay. Each lists item name, fields used, which templated file references it, and why. These files are *the* source of truth for "what does this bootstrap need from Bitwarden." Writing them is part of Phase 2 implementation, not an afterthought. (See "Secrets manifest split vs combined" below.)

### Bitwarden item conventions

In Bitwarden, organize as:

```
Folder: dotfiles-bootstrap/
  - GitHub Personal Token       (login: token in password)
  - AWS Personal SSO            (note: account_id, sso_url)
  - AWS work SSO             (note: account_id, sso_url)
  - Anthropic API Key           (login: key in password)
  - Raycast License             (note: license key, account email)
  - <other secrets as needed>
```

Item naming gets confirmed during Discovery review (see §15 Q-PARENT note). Phase 2 just consumes whatever's in `secrets.md`.

Reference in templates as:

```
api_key = {{ (bitwardenFields "item" "Anthropic API Key").api_key.value }}
```

### Session lifecycle

- `scripts/steps/P2-00-bitwarden-unlock.sh` writes `BW_SESSION` to `~/.local/state/macbook-setup/bw-session` with mode `0600`.
- Subsequent steps source it. The Phase 2 orchestrator threads `BW_SESSION` into the environment of every child step, so individual step scripts don't have to source the file themselves.
- Session file is deleted at end of bootstrap run, or after one hour, whichever comes first. Cleanup is implemented as a `trap` in the orchestrator plus a separate `at` (or background timer) that fires after 3600 seconds. Running Phase 2 again after expiry re-prompts for unlock.
- Re-running bootstrap re-unlocks; this is acceptable friction (parent §7 explicit decision).

### Secrets manifests — the per-overlay docs

Phase 2 produces and maintains a manifest in each overlay repo.

**Recommended (v1):** keep them split per repo for access-control symmetry. The personal manifest at the personal overlay's `docs/secrets.md` lists only items referenced by personal-overlay templates; the work manifest at the work overlay's `docs/secrets.md` lists only items referenced by work-overlay templates. Same rationale as the repo split itself: a coworker granted access to the work overlay for fleet standardisation should not also see the user's personal Bitwarden vault structure.

**Acceptable v1 alternative:** combined manifest at the personal overlay's `docs/secrets.md` listing both personal and work items, with the work overlay's `docs/` directory empty or pointing at the personal manifest. This is simpler to maintain but bleeds work-shape information into the personal repo. Pick this only if the access-control concern doesn't apply.

Format (used in either repo):

| Bitwarden item | Folder | Field(s) | Referenced from | Purpose |
|---|---|---|---|---|
| GitHub Personal Token | dotfiles-bootstrap | `password` | `home/private_dot_config/gh/hosts.yml.tmpl` (if used) | Optional fallback when SSH auth not preferred for a given host |
| AWS Personal SSO | dotfiles-bootstrap | note: `account_id`, `sso_url` | `dotfiles-private/home/private_dot_config/aws/config.tmpl` | SSO start URL + account ID for personal AWS profile |
| AWS work SSO | dotfiles-bootstrap | note: `account_id`, `sso_url` | `<work-overlay>/home/private_dot_config/aws/config.tmpl` | SSO start URL + account ID for work AWS profile |
| Anthropic API Key | dotfiles-bootstrap | login: `password` | `home/dot_claude/settings.json.tmpl` (only if not subscription-auth — usually unused) | API key for non-subscription Claude Code auth or other tools |
| Raycast License | dotfiles-bootstrap | note: `license_key`, `account_email` | `dotfiles-private/home/private_dot_config/raycast/...` | Raycast Pro license restoration |

The "Referenced from" column makes the manifest split natural: rows whose path begins `dotfiles-private/...` belong in the personal manifest; rows whose path begins `<work-overlay>/...` belong in the work manifest. Items referenced from both overlays (e.g., `Anthropic API Key` if used in both) are listed in both manifests.

Adding a new templated secret means: (1) add the Bitwarden item, (2) add the row to the appropriate manifest, (3) reference it from the template. Skipping step 2 is an authoring error caught in code review.

### A note on SSH commit signing

Q-PARENT-4 resolved in favor of **SSH commit signing**, not GPG. The Phase 0 step P0-40 already generated `~/.ssh/id_ed25519`; Phase 1's gitconfig template sets the `[user] signingkey` and `[gpg] format = ssh` entries pointing at `~/.ssh/id_ed25519.pub`. Phase 2 does not generate any new key — the SSH key from Phase 0 is reused for both auth and commit signing.

The private SSH config template (`home/private_dot_ssh/config.tmpl`) explicitly references `~/.ssh/id_ed25519` as the `IdentityFile` for relevant hosts. The private key file itself is *never* chezmoi-managed; it lives on disk only, generated once by Phase 0, never templated, never copied. If a new machine ever needs a new key, that's a P0-40 re-run, not a Phase 2 concern.

There is no GPG step. `gpg` is not installed by Phase 0, Phase 1, or Phase 2. If a future need for GPG arises (e.g., signing email, encrypting backups), it gets its own PRD.

## 8. Claude Code Plugins & Marketplace

Migrated from parent §8 verbatim. This section is **Phase 2's authoritative source** on the plugin boundary; parent §8 is the same content, repeated here for self-containment.

Claude Code's `~/.claude/` directory is split between two ownership models: a small slice managed by chezmoi (settings and global system prompt), and everything else delegated to Claude Code's own plugin and marketplace system.

### What chezmoi manages

Only files that are pure config and benefit from templating:

- `~/.claude/settings.json` — global Claude Code settings (model, permissions, theme, hooks). Templated to vary by `machine` (work vs personal).
- `~/.claude/CLAUDE.md` — global system prompt fragment applied to every conversation. Templated for machine-specific context (e.g., "this is a work machine, default to work-org conventions").

Both live as `.tmpl` files under `home/dot_claude/` in the public dotfiles repo.

**Never managed by chezmoi:**
- `~/.claude/.credentials.json` (auth tokens, never tracked anywhere)
- Skills, commands, agents, hooks, plugins, marketplaces (delegated below)

### What Claude Code's plugin system manages

Skills, commands, agents, and hooks are content, not config. They have their own lifecycles, their own repos, their own development loops. They belong to Claude Code's plugin/marketplace machinery, not to chezmoi.

The active path:

- **Personal plugin: `suTerminus/ghost-bazaar`.** A Claude Code plugin (or collection thereof) holding personal skills, commands, agents, and hooks. Cloned to `~/code/personal/ghost-bazaar` via the personal overlay's `repos-personal.yaml` (Phase 2 step P2-30). Installed into Claude Code via whatever the current plugin install command is (Phase 2 step P2-40 — see "Implementation note" below).
- **Team marketplace: the work-org marketplace.** Cloned to `~/code/<work-org>/claude-marketplace` via the work overlay's `repos-<work>.yaml` (Phase 2 step P2-30, work machines only — *not* by Phase 1 anymore). *Additionally* registered as a Claude Code marketplace by Phase 2 step P2-40, so plugins from it can be browsed and installed via Claude Code's marketplace commands. Cloning gives source visibility for editing/contributing; marketplace registration is what makes it usable inside Claude Code. On personal machines the marketplace is never cloned and never registered.

### Why no symlinks, no copies

Earlier drafts considered symlinking `~/.claude/skills/` → `ghost-bazaar/skills/`. Rejected for these reasons:

- The plugin/manifest system is the actively-developed, supported path. Riding it means inheriting future improvements.
- Symlinks are a custom convention to document and remember; manifests are documented by Anthropic.
- Marketplaces compose naturally — a team marketplace plus a personal plugin is exactly what marketplaces exist to handle. Symlinking would erase that boundary.
- No copying between `ghost-bazaar` and `claude-marketplace`. If something graduates from personal to team-shared, it moves cleanly with git history. Copies drift.

### Implementation note

**The exact plugin manifest format, install commands, and marketplace registration mechanism may have evolved between when this PRD was written and when Phase 2 actually runs.** The PRD intentionally doesn't pin them down.

Phase 2 responsibility: when wiring `ghost-bazaar` and registering the work-org marketplace, the agent (Claude Code on the target machine) must:

1. Read current Claude Code plugin/marketplace docs.
2. Verify ghost-bazaar's structure conforms to current expectations (manifest location, expected subdirectories for skills/commands/agents/hooks).
3. Adapt repo structure if needed before installing.
4. Use whatever install commands are current at the time, not historical guesses.

This delegation is deliberate. It costs a few minutes of doc-checking on the target machine and saves the PRD from going stale.

### Phase 1 vs Phase 2 boundary

- **Phase 1** clones whatever is in public `repos.yaml`. With the new three-repo model, public `repos.yaml` contains zero work-org entries — they all moved to `<work-overlay>/inventory/repos-<work>.yaml`. Phase 1 therefore does **not** clone the work-org marketplace anymore, does **not** clone `ghost-bazaar` (which lives in `repos-personal.yaml`), and does **not** install or register anything in Claude Code.
- **Phase 2** clones `ghost-bazaar` from the personal overlay's `repos-personal.yaml` (P2-30, always). On work machines, P2-30 also clones the work-org marketplace, the work-org docs repo, the work-org postgresql repo, etc., from the work overlay's `repos-<work>.yaml`. P2-40 then installs `ghost-bazaar` as a Claude Code plugin and (work only) registers the work-org marketplace as a Claude Code marketplace.

This means the very first Claude Code conversations on the new machine (during Phase 1 buildout) run with stock configuration. Personal skills and the team marketplace become available only after Phase 2. That's fine — Phase 1 work is mostly bash and YAML, neither of which needs custom skills.

### Smoke test as part of P2-40 acceptance

P2-40 doesn't terminate when install commands return success — it terminates when a known ghost-bazaar skill *runs* successfully end-to-end. The smoke test:

1. Open a fresh Claude Code session in `~/code/personal/dotfiles` (or wherever the smoke-test instructions are kept).
2. Invoke a known skill (defined in `ghost-bazaar/docs/smoke-test.md`).
3. Confirm the skill is recognized and produces the expected output.
4. Repeat for a known marketplace plugin from the work-org marketplace.

Failure of either check fails the step. This catches the failure mode where install commands succeeded but the manifest was misnamed, the plugin path wasn't picked up, or the marketplace wasn't registered correctly. Without the smoke test, those errors only surface much later, in the middle of unrelated work.

## 9. App Support snapshots (Raycast)

Resolution of Q-PARENT-6: per-app `~/Library/Application Support/` overlays. v1 ships Raycast only. Raycast belongs to the personal overlay — a personal app with personal state (Raycast Pro license, settings export).

### Layout

```
<personal-overlay>/home/private_dot_config/
└── raycast/
    └── ...                       # Raycast preferences and settings export
```

The directory is under `private_dot_config` so the apply-time mode is `0600` (the Raycast license file in particular).

### Apply-time hazards

Raycast holds its config in memory while running. Writing the files out from chezmoi while it's running can cause Raycast to overwrite the new files with its in-memory state on next save. Mitigation: quit Raycast before running `chezmoi apply` for the personal overlay if you have changes to push.

### Raycast license

Raycast Pro's license key lives in the user's Bitwarden vault (item name: `Raycast License`, see §7 manifest). The Raycast config files in `home/private_dot_config/raycast/...` reference the license through a chezmoi template if Raycast supports loading it from a settings file. If Raycast requires manual entry through the GUI, the bootstrap surfaces this as a one-time post-install step in Phase 3's manual-installs check.

### Why only one app in v1

The Discovery PRD §6 catalogs apps; the parent PRD §10 question 6 raised the broader question of which apps need App Support backups. v1 ships the one app where the user has explicit config worth tracking. Other apps (Slack, Spotify, browsers) are excluded — their config either syncs via the app's own account system or isn't worth bootstrapping. New apps can be added incrementally as an additive change in a future Phase-2 iteration.

## 10. Idempotency Contract (Phase 2)

Same model as Phase 0 PRD §7 and parent PRD §4, restated here for clarity:

- Every step probes before acting. If the probe passes, the step prints `skip` and exits 0.
- Every step is independently runnable. `scripts/steps/P2-20-brew-bundle-overlays.sh` works without orchestrator context (it sources `lib/` itself and assumes `BW_SESSION` is in env or the session file exists).
- Re-running Phase 2's orchestrator on a fully configured machine should complete in **under 30 seconds** with all steps showing `skip` (parent §12 success criterion, applied per-phase).
- A failed step does not corrupt prior steps. The orchestrator collects errors and reports at the end. `--fail-fast` opt-in.
- `--dry-run` runs all probes and prints what would happen without executing modifying commands. For P2-40, `--dry-run` runs the doc-fetch and manifest-verify steps but does not run install or registration commands.
- Step IDs follow the `P2-XX` scheme. Public dotfiles `scripts/steps/` directory therefore has files named `P2-00-bitwarden-unlock.sh`, `P2-10-personal-overlay.sh`, `P2-12-work-org-overlay.sh`, `P2-20-brew-bundle-overlays.sh`, `P2-30-clone-overlay-repos.sh`, `P2-40-plugin-and-marketplace.sh`, distinct from Phase 0's `00-` through `60-` and Phase 1's TBD numbering. P2-12 uses the `-12` slot (rather than the dense `-20` slot) because it's conditional and may be skipped on personal machines; the gap leaves numerical room for related future steps without disturbing the dense numbering of mandatory steps.

## 11. Iteration & Testing

Phase 2 testing builds on Phase 1's VM workflow. The recommended VM target is a snapshot taken **immediately after Phase 1 completes successfully** — that's the entry condition for Phase 2, so testing starts there.

### VM snapshot lineage

| Snapshot | Captures |
|---|---|
| `clean-sequoia` | Fresh macOS 15 Sequoia, signed-in user account |
| `phase0-complete` | After `phase0/bootstrap.sh` finishes |
| `phase1-complete` | After Phase 1 doctor (its scope) returns green |
| `phase2-complete` | After Phase 2 doctor returns green — used as Phase 3 entry |

Phase 2 iteration: restore `phase1-complete`, run Phase 2, observe, restore, fix, repeat. UTM with a Sequoia image is the recommended baseline.

### Probes (Phase 2 doctor scope)

`scripts/doctor.sh` (Phase 3 owns the full multi-phase doctor; Phase 2 contributes its checks):

- `bw status` returns `unlocked` *while a session file is valid* (not during normal idle). Doctor reports `[skipped: no active session]` when the session file is absent — this is healthy for an idle machine, not an error.
- `chezmoi diff --source ~/.local/share/chezmoi-private` is empty.
- If `machine == "work"`: `chezmoi diff --source ~/.local/share/chezmoi-<work>` is empty.
- If `machine == "personal"`: `~/.local/share/chezmoi-<work>` does **not** exist. Existence on a personal machine is reported as drift.
- For `~/.config/brew/Brewfile.personal`: `brew bundle check --file=...` returns 0. If `machine == "work"`, also for `Brewfile.work-org`.
- For each entry in `repos-personal.yaml` (always) and `repos-<work>.yaml` (work only): target dir exists and is a git repo with the expected origin.
- `aws sso login --profile <profile>` smoke test: at least one configured profile completes auth without error. (This is interactive; doctor flags it for manual run, doesn't auto-trigger.)
- `claude` lists `ghost-bazaar` plugin (always). On work machines, also the work-org marketplace registered.
- A canary skill from `ghost-bazaar` invokes successfully (`ghost-bazaar/docs/smoke-test.md` describes how).

### What to expect breaking

- **Bitwarden 2FA timing.** If 2FA codes expire during a long Phase 2 run, BW templates in later steps fail to render. Mitigation: complete Phase 2 in one sitting; don't pause partway.
- **Missing Bitwarden items.** A template references `(bitwardenFields "item" "Foo").bar.value` but `Foo` doesn't exist. chezmoi templates fail loudly here, not silently — verify by trying to apply with one item temporarily renamed in the vault and confirming the failure surfaces.
- **MAS sign-in not yet performed.** P2-20 catches this and warns rather than failing the step (per Brewfile).
- **Overlay apply order skipped.** Running P2-12 manually on a work machine without P2-10 having run produces the work overlay applied directly on top of public, with personal AWS profiles missing. The orchestrator preflight catches this; manual single-step invocation does not.
- **Claude Code plugin commands evolved.** P2-40 explicitly handles this via doc-check at runtime.
- **Raycast running during apply.** Causes config drift. Documented in §9.

## 14. Success Criteria

A subset of parent §12, scoped to Phase 2:

- After Phase 2 completes, `chezmoi diff` against the public source and the personal overlay returns empty (always); against the work overlay returns empty on work machines and the source dir does not exist on personal machines. Re-running Phase 2 takes under 30 seconds with all steps `skip`.
- **Personal-machine isolation.** On a `personal` machine, the work overlay is never cloned and never applied. Verifying that `~/.local/share/chezmoi-<work>` does not exist is part of the doctor probe set (§11). Verifying that no work-only Brewfile entries (Slack, work chat, corporate VPN client, etc.) were installed is implied by the personal Brewfile being the only Brewfile bundled.
- **Work-machine cleanliness.** On a `work` machine, all three sources apply cleanly with no conflicts: `chezmoi diff` against public, personal, and work-org sources is each empty. AWS config contains both personal and work SSO profiles (the work overlay layers on top without removing personal entries — this is the behavior the §3 ordering guarantees).
- Every file under a `private_*`-prefixed path lands on disk with mode `0600`. Verified via `find ~/.ssh ~/.config/aws -type f -exec stat -f '%Mp' {} \;` (or equivalent), expecting `600` for every file.
- All Bitwarden-templated files render correctly with values pulled from the vault. A missing Bitwarden item produces a clear apply-time error, not a silent empty render. (Test: rename one item in vault temporarily; confirm chezmoi apply fails loudly.)
- `aws sso login --profile <profile>` succeeds for at least one configured profile without manual config edits. (Smoke test, run once after Phase 2.)
- `ghost-bazaar` plugin is installed and a smoke-test skill executes end-to-end (always). On work machines, the work-org marketplace is registered and a smoke-test plugin from it is reachable.
- The public repo passes a final secrets-leak audit: `grep -rEi '(api[_-]?key|secret|token|password)' ~/code/personal/dotfiles/` returns only matches that are clearly *names of templates referencing secrets*, never literal secret values. Same audit on the rendered targets confirms private files contain real secret material (expected, since they were rendered from the vault).
- Each overlay's `docs/secrets.md` lists every Bitwarden item used by templates in that overlay. Cross-check: `grep -rE 'bitwarden(Fields|Attachment)' ~/.local/share/chezmoi-private/` produces only items named in the personal overlay's `docs/secrets.md`; same check against `~/.local/share/chezmoi-<work>/` against the work manifest.

The git `signingkey` config lives in the **public** dotfiles repo's gitconfig template (Phase 1) — it points to the public key path `~/.ssh/id_ed25519.pub`, which is a path, not a secret. The actual private key file is never chezmoi-managed and never templated. No GPG step exists in any phase. If GPG ever becomes necessary, it gets a new PRD.

If individual skills become shareable over time, they can move out into the work-org marketplace (for team-shared) or into a hypothetical `suTerminus/ghost-bazaar-public` (for personal-shareable) at that point. - **Q-PARENT-6 (App Support backups for specific apps). RESOLVED for v1.** Raycast only. Phase 2 owns the chezmoi entry (under `private_dot_config/`). Other apps (Slack, Spotify, browsers, etc.) explicitly excluded — their config either syncs via account or isn't worth bootstrapping. Adding more apps later is an additive change.
- **Bitwarden item naming.** The exact item names in `secrets.md` get confirmed during Discovery review (looking at the user's existing vault structure). Phase 2 just consumes whatever names Discovery decides on. Renaming items later is a cross-cut change: rename in vault, update `secrets.md`, update every template that references the old name. Discovery is the right time to lock these in once.
- **Phase 2 doctor vs Phase 3 doctor.** Phase 2 ships its own probes (§11). Phase 3 owns the unified `scripts/doctor.sh`. The boundary: Phase 2's probes live in their own functions and are *imported* by the Phase 3 doctor — not duplicated. This requires a small refactor at the Phase 3 boundary; Phase 2 just makes its probes importable from the start.
- **Q-NEW: Apply work overlay on a `personal` machine for testing?** Should there be a way to apply the work overlay on a strictly-personal machine (e.g., for development/testing of work configs without committing to the work machine type)? **Recommendation: no v1 escape hatch.** A `--include-tag work-org-test` flag, an environment override, or a "shadow" mode are all over-engineering for a one-developer scenario. If testing is needed, manually flip the `machine` chezmoi prompt to `work`, re-run Phase 2, then flip back. The cost of that workflow on a developer's own machine is acceptable; the cost of carrying a permanent escape-hatch flag with its own edge cases is not.
