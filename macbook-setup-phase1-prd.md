# PRD Addendum: Phase 1 — Inventory System, chezmoi, Public Dotfiles

**Owner:** Berkay
**Status:** Draft v1
**Parent doc:** `macbook-setup-prd.md`
**Sibling docs:** `macbook-setup-discovery-prd.md`, `macbook-setup-phase0-prd.md`, `macbook-setup-phase2-prd.md`, `macbook-setup-phase3-prd.md`
**Goal:** After Phase 0 hands off, Claude Code drives chezmoi init+apply, the public Brewfile pipeline, mise + language tools, and public repo cloning. Exit state: a working public-dotfiles environment with all declared CLIs and language runtimes installed.

---

## 1. Phase Boundary

Phase 1 has a hard entry condition and a hard exit condition. Both are checkable; both are how the phase model stays a real boundary instead of a marketing slogan.

**Entry state.** Phase 0 has run to completion on the target machine. Specifically:

- The marker file `~/.local/state/macbook-setup/.phase0-complete` exists and is non-empty (it contains the timestamp at which Phase 0 finished).
- Claude Code is installed, authenticated, and being driven from the working tree at `~/code/personal/dotfiles`. Phase 1 is conversational: the human runs `claude` inside the cloned repo and asks Claude Code to drive Phase 1.
- The four Phase 0 packages (`gh`, `git`, `node`, `jq`) are present on `$PATH`. Phase 1 also assumes Homebrew itself is functional and `~/.zprofile` sources `brew shellenv`.
- The repo on disk matches the structure documented in this PRD's §3 (i.e., the work described here has been merged into the public dotfiles repo before the new machine is brought up).

If any of these are missing, Phase 1's preflight step (`P1-00`) fails fast with a pointer back to Phase 0.

**Exit state.** Phase 1 is "complete" when:

- chezmoi has been initialized against the working repo and `chezmoi diff` against the rendered targets is empty.
- The public Brewfile (`~/.config/brew/Brewfile`) has been rendered from `inventory/brew.yaml` and `brew bundle check` against it returns 0.
- All non-optional `mise` tools from `inventory/mise.yaml` are installed and `mise current` reports the expected defaults; declared `python_tools` are installed via `uv tool install`.
- All public repos in `inventory/repos.yaml` (machine-type filtered, non-optional) exist on disk at their declared paths with the declared remote.
- A marker file `~/.local/state/macbook-setup/.phase1-complete` has been written.

Phase 1 explicitly does **not** require Bitwarden auth, the private overlay, marketplace registration, or any macOS defaults. Those belong to Phase 2 and Phase 3 respectively. If MAS apps are declared in `inventory/brew.yaml` and the user is not signed into the App Store, Phase 1 logs a warning and continues — it does not fail.

The exit state is checkable by re-running `./scripts/setup.sh --doctor`, which runs every step's idempotency probe and reports `[ok] / [drift] / [missing]` per item. The exit-state contract is "doctor is all green for Phase 1's scope."

## 2. Phase 1 Scope

The bulk of the parent PRD's day-to-day tooling is Phase 1's responsibility. The split below is deliberate: anything that touches secrets, private repos, marketplace registration, or system preferences is deferred. Anything that's safe to run with stock public configuration runs here.

### In scope

| Area | What Phase 1 does |
|---|---|
| chezmoi | `chezmoi init --apply --source ~/code/personal/dotfiles`, render every `.tmpl` under `home/` to its target, populate `~/.config/git/config`, `~/.zshrc`, `~/.config/mise/config.toml`, `~/.config/brew/Brewfile`. |
| `.chezmoi.toml.tmpl` | First-run prompts for `machine` (work / personal), `name`, `email`. Stored at `~/.config/chezmoi/chezmoi.toml`, read on subsequent applies. |
| `.chezmoiignore.tmpl` | Templated. Gates work-only files on `.machine == "personal"` and vice versa. |
| Brewfile pipeline | `scripts/render-brewfile.sh` reads `inventory/brew.yaml` and writes `home/dot_config/brew/Brewfile.tmpl`; chezmoi then renders it to `~/.config/brew/Brewfile`; `brew bundle install` consumes that. |
| Public Brewfile bundle | `brew bundle install --file=~/.config/brew/Brewfile`, including any `mas` lines (warn-not-fail if MAS unauthenticated). |
| mise | Install `mise` itself (covered by Brewfile), render `~/.config/mise/config.toml` from `inventory/mise.yaml` via chezmoi template, then `mise install`. |
| Python tooling | `uv tool install <pkg>` for every entry in `inventory/mise.yaml -> python_tools`, idempotent per-tool. |
| Public repo clone | Read `inventory/repos.yaml`, clone every entry (machine-type and tag-filtered) to its declared path. Skip existing clones; opt-in pull via `--update-repos`. |
| Git identity | `home/dot_gitconfig.tmpl` and `home/dot_config/git/config.tmpl` set `user.name`, `user.email`, signing config. SSH commit signing using the key generated by Phase 0 step `P0-40`. |

### Out of scope

| Area | Phase | Why |
|---|---|---|
| Bitwarden CLI auth + session | Phase 2 | Secrets aren't needed for any Phase 1 step. Keeping `bw` out of Phase 1 means Phase 1 can run without Bitwarden being set up. |
| Personal dotfiles overlay (`suTerminus/dotfiles-private`) | Phase 2 | Phase 1's exit state is "public dotfiles working." Personal overlay is the next layer (P2-10). |
| Work dotfiles overlay | Phase 2 | Conditional on `machine == "work"`; applied after personal overlay (P2-12). |
| Work-org marketplace clone + registration | Phase 2 | Lives in the work overlay's `repos-<work>.yaml`, not in public `repos.yaml`. Phase 1 does NOT clone any work-org repos. |
| `suTerminus/ghost-bazaar` (private) | Phase 2 | Lives in `dotfiles-private/inventory/repos-personal.yaml`, which Phase 1 does not read. |
| AWS profiles, work-specific tools requiring secrets | Phase 2 | All depend on Bitwarden. |
| macOS `defaults write` | Phase 3 | Cosmetic / system-wide preferences. Don't block development tooling on them. |
| Touch ID for sudo (`pam_tid.so` in `/etc/pam.d/sudo_local`) | Phase 3 | Polish; not needed for any Phase 1 step. |
| `scripts/doctor.sh` standalone | Phase 3 | Phase 1 ships `--doctor` as a thin alias to `setup.sh --dry-run --all`; the dedicated doctor with full reporting is Phase 3. |
| Manual-install detection (`inventory/manual.yaml`) | Phase 3 | Discovery captures these but no Phase 1 step depends on them. |

Cross-references: see `macbook-setup-phase2-prd.md` for the private overlay, Bitwarden, marketplace, and ghost-bazaar work; see `macbook-setup-phase3-prd.md` for macOS defaults, Touch ID sudo, and the doctor script.

## 3. Repository Layout (Phase 1 contributions)

This is the **delta** Phase 1 introduces inside the public dotfiles repo. The full repo tree is in the parent PRD §3; only files added or first-touched by Phase 1 are listed here. Files prefixed `home/dot_*` are chezmoi source names; their rendered targets are shown in parentheses.

```
│   ├── dot_config/

│   │   │   └── config.tmpl                          # → ~/.config/git/config (identity + signing)
│   │   ├── mise/
│   │   │   └── config.toml.tmpl                     # → ~/.config/mise/config.toml
│   │   └── brew/

│   ├── repos.yaml                                   # public repo list
│   └── mise.yaml                                    # language versions + python_tools
└── scripts/
    ├── setup.sh                                     # Phase 1+ orchestrator
    ├── render-brewfile.sh                           # yq → home/dot_config/brew/Brewfile.tmpl
    ├── lib/
    │   ├── log.sh                                   # info / warn / error / ok / skip helpers
    │   ├── idempotent.sh                            # ensure_* probes
    │   └── prompt.sh                                # interactive prompts (re-used by chezmoi.toml.tmpl flows)
    └── steps/
        ├── P1-00-preflight.sh
        ├── P1-10-chezmoi-init.sh
        ├── P1-20-render-brewfile.sh
        ├── P1-30-brew-bundle.sh
        ├── P1-40-mise-install.sh
        └── P1-50-clone-public-repos.sh
```

**Notes:**

- `phase0/` and `scripts/` are **outside** `home/`, which is what `.chezmoiroot=home` means: chezmoi only sees `home/` as its source. So neither `.chezmoiignore` nor any chezmoi config has to mention them. They're invisible.
- Per the decision baked into this PRD, chezmoi's source dir is set in `.chezmoi.toml.tmpl` to `{{ .chezmoi.homeDir }}/code/personal/dotfiles` (i.e., the working repo, not the default `~/.local/share/chezmoi`). This means `chezmoi apply` reads from the same directory the human edits in. The parent PRD §6 discussed both options and explicitly recommended pointing at the working repo.
- `home/dot_gitconfig.tmpl` is intentionally minimal (single-line `[include] path = ~/.config/git/config`). The real gitconfig content is at `home/dot_config/git/config.tmpl` so it's editable as XDG-style config without fighting `dot_` prefix conventions.
- Step files use the dense `P1-NN` naming. The legacy 50/60/70/80/85/90 spacing from the parent PRD §4 is replaced here with `P1-00, P1-10, P1-20, P1-30, P1-40, P1-50`. This is deliberate: the parent table will be updated to match (M0.T07).

The full repo tree (including future phases' contributions) is in `macbook-setup-prd.md` §3; refer there rather than duplicating.

## 4. The Phase 1 Flow

Phase 1 is invoked by Claude Code. The human's job in Phase 1 is approximately: open a Claude Code session, point it at this PRD, and approve / answer prompts. Claude Code's job is to run `setup.sh` with the right flags, interpret output, and intervene on errors.

### Entry point

```
cd ~/code/personal/dotfiles
./scripts/setup.sh --only P1-00,P1-10,P1-20,P1-30,P1-40,P1-50
```

Equivalently, `--phase 1` is an alias that selects every `P1-*` step in order. Either form works; the `--only` form is preferred in conversation because it's explicit about what runs.

### Orchestrator behavior

`scripts/setup.sh` sources `scripts/lib/log.sh`, `scripts/lib/idempotent.sh`, `scripts/lib/prompt.sh`. It parses flags, then iterates `scripts/steps/P1-*.sh` (or whatever the `--only` filter resolves to) in lexical order. For each step:

1. Print a header (`P1-20 render-brewfile`).
2. Source the step file. Each step is a function `run` that returns 0 on success / skip, non-zero on hard error.
3. Capture exit code, elapsed time, and the step's `idempotency_probe` result (set as a string by the step before it acts).
4. On error: by default, log and continue. With `--fail-fast`: exit immediately.
5. At the end, print a summary table: step / status / probe / duration.

### Flags

| Flag | Behavior |
|---|---|
| `--only <step,...>` | Run only the listed step IDs. |
| `--phase <N>` | Run all steps whose ID matches `P<N>-*`. Phase 1 alias. |
| `--skip <step,...>` | Run everything except the listed steps. |
| `--include-tag <tag>` | Activate the named tag bucket (e.g., `--include-tag gis` to install QGIS). Passed through to the Brewfile renderer and the repo cloner. |
| `--update-repos` | In `P1-50`, pull existing clones in addition to cloning missing ones. Off by default. |
| `--dry-run` | Run every probe; print what would happen; don't execute modifying commands. Brewfile renderer runs in diff mode. |
| `--doctor` | Alias for `--dry-run --phase 1` plus an explicit summary line per step. (The full doctor with `[ok]/[drift]/[missing]` reporting is a Phase 3 deliverable; this is the Phase 1 stub.) |
| `--fail-fast` | Stop on first error instead of collecting and reporting at the end. |

### Logging

Same shape as Phase 0 (cf. `macbook-setup-phase0-prd.md` §4):

- Full output captured to `~/.local/state/macbook-setup/run-<timestamp>.log`.
- Colored, human-readable summary to stdout.
- Each step uses `info / ok / skip / warn / error` from `lib/log.sh`.
- `skip` is first class — most re-run steps will print `skip: already <X>`.

### Standalone steps

Each step file under `scripts/steps/` is independently runnable:

```
./scripts/steps/P1-20-render-brewfile.sh
./scripts/steps/P1-30-brew-bundle.sh
```

The step file sources `lib/` itself; it does not depend on the orchestrator. This matters during iteration — Claude Code can re-run a single step in conversation without re-running the world.

## 5. Step Specifications

Format identical to `macbook-setup-phase0-prd.md` §5: each step has **Probe**, **Behavior**, **Notes**.

### P1-00 preflight

**Probe:** `~/.local/state/macbook-setup/.phase0-complete` exists and is non-empty.

**Behavior:**

- If the marker file is present: emit `ok: phase 0 marker found (<timestamp>)`.
- Verify the cwd is `~/code/personal/dotfiles` (or that `$DOTFILES_DIR` is set and matches). If not, error with a hint.
- Verify `gh auth status` exits 0 and reports SSH protocol (Phase 0 set this up; if a re-image broke it, fail loud).
- Verify `command -v brew` resolves and `brew --version` succeeds.
- Verify `~/.ssh/id_ed25519.pub` exists (used by SSH commit signing in `P1-10`).
- If all checks pass: `ok` and continue. Otherwise: `error` with the specific missing precondition.

**Notes:**

- Preflight does **not** mutate. It reads. This is so `--dry-run` is meaningful from the very first step.
- The cwd check exists because `chezmoi` will read the source dir from `.chezmoi.toml`, but `setup.sh` and `render-brewfile.sh` use relative paths. Anchoring at the working repo prevents subtle path bugs.
- If `id_ed25519.pub` is missing, Phase 0 step `P0-40` (github-auth) didn't actually generate a key. Don't try to fix it here; point back at Phase 0.

### P1-10 chezmoi-init

**Probe:** `chezmoi source-path` returns a path equal to `~/code/personal/dotfiles/home`. If the path is wrong (e.g., still pointing at `~/.local/share/chezmoi`) or chezmoi isn't initialized, the probe fails.

**Behavior:**

- If chezmoi is not yet installed: install via `brew install chezmoi`. (It's also in `inventory/brew.yaml`, but `P1-30` runs after `P1-10`, so we install it eagerly here.) Skip if already installed.
- If chezmoi has never been initialized on this machine: `chezmoi init --apply --source ~/code/personal/dotfiles`.
  - This triggers the prompts in `home/.chezmoi.toml.tmpl`: `machine` (work / personal), `name`, `email`. Answers persist to `~/.config/chezmoi/chezmoi.toml`.
  - The `--apply` flag renders every templated file under `home/` to its target.
- If chezmoi has already been initialized: `chezmoi apply`. This is the idempotent path.
- After apply, run `chezmoi diff`. The output should be empty. If non-empty, log a warning with the diff content (don't fail — the user may have local edits the agent should know about).

**Notes:**

- Source dir is set via `--source` on first init **and** locked in via `~/.config/chezmoi/chezmoi.toml`. Subsequent `chezmoi apply` reads from the config.
- `home/.chezmoi.toml.tmpl` prompts use chezmoi's `promptString` and `promptChoice` helpers. The values populate `data.machine`, `data.name`, `data.email`, which then drive every other template (notably gitconfig and `.chezmoiignore.tmpl`).
- Files rendered by this step include: `~/.zshrc`, `~/.gitconfig`, `~/.config/git/config`, `~/.config/mise/config.toml`, **and** `~/.config/brew/Brewfile`. The Brewfile target is downstream of `P1-20` rendering its template — see §7 for the pipeline.
- Git identity (`user.name`, `user.email`) and SSH commit signing config (`gpg.format=ssh`, `user.signingkey=~/.ssh/id_ed25519.pub`, `commit.gpgsign=true`) are baked into `home/dot_config/git/config.tmpl`. The signing key reuses the SSH key generated in Phase 0 step `P0-40` — no new key generation.
- `home/.chezmoiignore.tmpl` is a templated chezmoi ignore. It uses `{{ if eq .machine "personal" }}...{{ end }}` blocks to ignore work-only `home/` files on personal machines (e.g., a hypothetical `home/dot_config/aws/` once the work overlay merges in via Phase 2). For Phase 1's contributions, the ignore is mostly empty — the files we add here are universal — but the templating scaffold is set up so Phase 2 doesn't have to touch the ignore-file format.

### P1-20 render-brewfile

**Probe:** `home/dot_config/brew/Brewfile.tmpl` exists AND its mtime is greater than or equal to `inventory/brew.yaml` mtime AND no `--include-tag` or `--machine` override would change the rendered output.

**Behavior:**

- If the probe passes and we're not in `--dry-run`: `skip: Brewfile.tmpl up to date`.
- Else: run `scripts/render-brewfile.sh`.
  - Reads `inventory/brew.yaml` via `yq`.
  - Filters out entries whose tags include `optional` unless the corresponding tag is in `--include-tag`.
  - Filters by machine-type tags (`work` / `personal`) using the value chezmoi prompted for. (The renderer reads it from `~/.config/chezmoi/chezmoi.toml` directly, so it doesn't need to be re-prompted.)
  - Emits a chezmoi-templated Brewfile to `home/dot_config/brew/Brewfile.tmpl`. The template is itself templated: where the renderer needs runtime branching (e.g., MAS apps that should appear only on work machines), it emits `{{ if eq .machine "work" }}...{{ end }}` blocks. Where it can resolve at render time (tag filtering with `--include-tag`), it bakes the result in.
- After render, if `chezmoi` is initialized, run `chezmoi apply --include=files dot_config/brew/Brewfile` to re-render the final `~/.config/brew/Brewfile`. Otherwise leave the apply for `P1-10`'s next pass; this matters if `P1-20` is run standalone before `P1-10`.

**Notes:**

- Tag filtering: `tags: [optional, gis]` means the entry is rendered only when `--include-tag gis` is passed. The full tag-semantics block is inherited from the parent PRD §5; see also §6 of this PRD.
- Machine-conditional includes are emitted as chezmoi template fragments rather than resolved at render time, on purpose: it lets the same `Brewfile.tmpl` work on both work and personal machines without rerunning the renderer when machine type changes (rare, but cleaner this way).
- The renderer is a separate step (and a separate script) rather than a chezmoi `run_once_` hook. The decision: easier to test, easier to invoke from `setup.sh --dry-run`, easier to reason about. A chezmoi hook would tie rendering to apply-time, which is fine in production but annoying during iteration.
- If `inventory/brew.yaml` parses but yields zero entries, the renderer emits a `Brewfile.tmpl` that's a comment-only file. It does not error; an empty Brewfile is legal.

### P1-30 brew-bundle

**Probe:** `brew bundle check --file=~/.config/brew/Brewfile` exits 0.

**Behavior:**

- If probe passes: `skip: brew bundle satisfied`.
- Else: `brew bundle install --file=~/.config/brew/Brewfile`.
- If the Brewfile contains `mas` lines, pre-check `mas account` before running bundle:
  - If `mas account` exits non-zero (App Store not signed in): emit `warn: not signed in to Mac App Store; mas entries will fail. Continuing.` Do not fail the step. The bundle command will print per-entry errors for MAS apps; those propagate as warnings.
- Re-check probe after install. If it still fails after install (i.e., bundle reported success but check still says missing), emit `warn` with the `brew bundle check` output, but exit 0 — this is almost always a MAS auth issue.

**Notes:**

- MAS warn-not-fail is a deliberate decision (open question Q-PARENT-3 in parent PRD; resolved here — see §13). Phase 1 must not be blocked by App Store auth state.
- Network flakiness: `brew bundle install` is reasonably good at retrying single-package failures, but full network outages will fail the step. The orchestrator's default behavior (continue on error) means Phase 1 won't crash on a transient network blip; the user can re-run.
- `~/.config/brew/Brewfile` is the rendered target of `home/dot_config/brew/Brewfile.tmpl`. The template path `home/Brewfile.tmpl` from the parent PRD §3 is **not** what we use; the actual location is the XDG-style `~/.config/brew/Brewfile`. This is a deliberate departure (noted as an inconsistency to be fixed in M0.T07).

### P1-40 mise-install

**Probe:** For every tool in `inventory/mise.yaml -> tools`, `mise current <tool>` returns the declared default version. For every package in `python_tools`, `uv tool list | grep -q <pkg>` succeeds.

**Behavior:**

- `mise install` — installs every version declared in `~/.config/mise/config.toml` (which chezmoi rendered in `P1-10` from `inventory/mise.yaml`). Per-version idempotency is mise's job; if a version is present, it's skipped silently.
- For each tool in `inventory/mise.yaml -> tools`, verify `mise current <tool>` returns the expected default. If not, `mise use --global <tool>@<version>`.
- For each entry in `inventory/mise.yaml -> python_tools`, run `uv tool install <pkg>` if not already installed (probe via `uv tool list`). Re-runs print `skip: <pkg> already installed`.

**Notes:**

- Idempotent re-runs: each tool prints either `ok: <tool>@<version> installed` or `skip: <tool>@<version> already installed`. This is per-tool, not per-step, so the output is informative on partial state.
- `uv` itself is installed via mise in `inventory/mise.yaml -> tools.uv.versions: [latest]`. So `uv tool install` is available by the time Phase 1 needs it.
- Python `python_tools` examples (from parent PRD §5): `nox`, `ruff`, `pre-commit`. The actual list is whatever Discovery + translation produced.
- This step does not configure shell activation for mise. That's done by `home/dot_zshrc.tmpl` (which adds `eval "$(mise activate zsh)"`), rendered by `P1-10`. As a result, `mise current` works in any new shell after Phase 1 completes.

### P1-50 clone-public-repos

**Probe:** For every repo entry in `inventory/repos.yaml` (machine-type and tag-filtered), the repo's declared `path` exists, contains a `.git/` directory, and `git -C <path> remote get-url origin` matches the declared URL.

**Behavior:**

- Read `inventory/repos.yaml`. Apply machine-type filter: a repo with `tags: [work]` is skipped on a personal machine; `tags: [personal]` on a work machine.
- Apply tag filter: a repo with `tags: [optional, ...]` is skipped unless the corresponding tag is in `--include-tag`.
- For each surviving entry:
  - If path exists and is a git repo with the right remote: `skip: <name> already cloned`. If `--update-repos` is set, also run `git -C <path> pull --ff-only` and report the result.
  - If path exists and is **not** a git repo: `error: <path> exists but is not a git repository`. Do not delete or touch it. Skip this entry, continue with the rest, return non-zero at the end of the step so the orchestrator surfaces it.
  - If path exists and has the wrong remote: `warn: <path> remote is <X>, expected <Y>`. Do not modify.
  - If path is missing: `mkdir -p $(dirname <path>) && git clone <url> <path>`.
- After the loop, summarize: `cloned: N; skipped: M; errors: K`.

**Notes:**

- Phase 1 reads only `inventory/repos.yaml` (public). It does **not** read the personal overlay's `repos-personal.yaml` or the work overlay's `repos-<work>.yaml` — those are Phase 2's job (P2-30). So personal-overlay and work-org repos are NOT cloned in Phase 1.
- Public `repos.yaml` does not contain any work-org entries — those moved to the work overlay's `repos-<work>.yaml` in the three-repo architecture.
- The "wrong remote" case is intentionally non-destructive. If the user has manually pointed a clone at a fork, Phase 1 should not silently undo that. A warning is enough; the human can investigate.
- Path expansion: `~` expands relative to `$HOME`. Absolute paths are honored as-is. The `defaults.base_path` from `repos.yaml` is the implicit root for entries that omit a leading `~/` or `/`.
- `--update-repos` is opt-in for one reason: pulling an arbitrary set of repos as a side effect of `setup.sh` re-runs leads to surprises ("why did my WIP branch get rebased?"). Default off; humans pull when they pull.

Phase 1 reads three inventory files: `inventory/brew.yaml`, `inventory/repos.yaml`, `inventory/mise.yaml`. The schema is reproduced here for self-containment, but the **content** is not invented here — it's produced by Discovery (see `macbook-setup-discovery-prd.md` §8: "Translation: Catalog → Inventory").

### `inventory/mise.yaml`

```yaml
# Becomes ~/.config/mise/config.toml via chezmoi template (P1-10),
# then `mise install` consumes it (P1-40).

tools:
  go:
    versions: ["1.23", "1.22"]
    default: "1.23"
  node:
    versions: ["20", "22"]
    default: "22"
  python:
    versions: ["3.12", "3.11"]
    default: "3.12"
  uv:
    versions: ["latest"]

# Python CLI tools installed via `uv tool install` (P1-40).
python_tools:
  - nox
  - ruff
  - pre-commit
```

### Tag semantics

Inherited verbatim from the parent PRD §5; restated here so Phase 1 step authors don't have to context-switch:

- A tool/repo/cask with **no tags** is always installed.
- A tool with `tags: [optional, ...]` is **skipped by default**; installed only when the run includes `--include-tag <tag>`.
- A tool with `tags: [work]` is installed only on machines where chezmoi's `data.machine == "work"`. Same for `personal`.
- Tags compose: `tags: [work, optional]` means "work machine + explicit `--include-tag` opt-in."
- Tags `meta`, `claude`, `docs`, `infra` etc. are descriptive only — they don't gate installation unless explicitly named in `--include-tag`.

The Phase 1 renderer (`scripts/render-brewfile.sh`) and cloner (`P1-50`) both implement these rules. They share helpers in `scripts/lib/idempotent.sh`.

The actual content of `brew.yaml`, `repos.yaml`, and `mise.yaml` is the output of Discovery + Translation. See `macbook-setup-discovery-prd.md` §5 for the catalog format and §8 for the translation step.

## 7. The Brewfile Pipeline

The Brewfile is a four-stage pipeline. This is the most opinionated decision in Phase 1 and worth a dedicated section.

```
inventory/brew.yaml ──[scripts/render-brewfile.sh]──> home/dot_config/brew/Brewfile.tmpl
                                                                │
                                                                ▼
                                                        [chezmoi apply]
                                                                │
                                                                ▼
                                                     ~/.config/brew/Brewfile
                                                                │
                                                                ▼
                                                     [brew bundle install]
```

Each arrow is a transition; each box is a file or command. The pipeline reads top to bottom.

**Stage 1: `inventory/brew.yaml` → `home/dot_config/brew/Brewfile.tmpl`.** Triggered by step `P1-20`. The script `scripts/render-brewfile.sh` reads the YAML via `yq`, applies tag and machine filters at render time where possible, and emits a chezmoi-flavored Brewfile template. Machine-conditional fragments are emitted as `{{ if eq .machine "..." }}...{{ end }}` blocks so the same template works for both `work` and `personal`. Optional buckets the user opted into via `--include-tag` are baked in; ones they didn't are omitted.

**Stage 2: `home/dot_config/brew/Brewfile.tmpl` → `~/.config/brew/Brewfile`.** Done by chezmoi during `chezmoi apply` (`P1-10`). chezmoi handles `dot_config` → `.config` name mangling and templating substitution. The output is plain Brewfile syntax, no chezmoi markers left.

**Stage 3: `~/.config/brew/Brewfile` is consumed by `brew bundle install`** in step `P1-30`. Brew's idempotency (`brew bundle check`) is the gate.

### Why a separate render step (and not just a chezmoi `run_once_` hook)

Two reasons:

1. **Testability.** `scripts/render-brewfile.sh` can be invoked directly with `--dry-run` or against a fixture YAML, without involving chezmoi. This matters during inventory authoring.
2. **Visibility.** The rendered `Brewfile.tmpl` is committed to the repo. Anyone reading `home/dot_config/brew/Brewfile.tmpl` sees exactly what chezmoi will hand to brew, with no hidden script step. If the `Brewfile.tmpl` is stale relative to `inventory/brew.yaml`, the `P1-20` probe catches it.

A `run_once_before_brewfile.tmpl` chezmoi hook would couple rendering to apply, which makes step ordering subtle and makes "render but don't apply" awkward.

### Forward reference: overlay Brewfiles (Phase 2)

The same renderer is reused by Phase 2 for overlay Brewfiles. Phase 2 introduces:

- `dotfiles-private/inventory/brew-personal.yaml` — personal-machine apps (always rendered into `~/.config/brew/Brewfile.personal`).
- Work overlay's `inventory/brew-<work>.yaml` — work-machine apps (rendered into `~/.config/brew/Brewfile.<work>` only when `machine == "work"`).

```
inventory/brew.yaml                                   ──[render-brewfile.sh]──> Brewfile.tmpl              (Phase 1)
dotfiles-private/inventory/brew-personal.yaml         ──[render-brewfile.sh]──> Brewfile.personal.tmpl    (Phase 2 P2-20)
work-overlay/inventory/brew-<work>.yaml               ──[render-brewfile.sh]──> Brewfile.<work>.tmpl       (Phase 2 P2-20, work-only)
```

The renderer treats each input independently — there is no merge. Each overlay produces its own templated Brewfile; `brew bundle` is invoked once per Brewfile by the relevant phase. Phase 1 only runs the public render; Phase 2 runs the overlay renders against whichever overlay sources exist.

## 8. Idempotency Contract (Phase 1)

Same shape as the parent PRD §4 "re-run semantics," restated for Phase 1's specific steps:

- **Every step probes before acting.** `lib/idempotent.sh` provides probe helpers. If the probe returns "already done," the step prints `skip: <reason>` and returns 0. No error is emitted, no work is duplicated.
- **Every step is independently runnable.** `scripts/steps/P1-30-brew-bundle.sh` works without the orchestrator: it sources `lib/log.sh` and `lib/idempotent.sh` itself. This is enforced by a smoke test in §9.
- **Re-running `setup.sh --phase 1` on a Phase-1-complete machine completes in under 30 seconds, with every step printing `skip`.** This is the headline number, equivalent to Phase 0's <15s target. The 2x budget reflects Phase 1's larger probe set (per-tool mise probes, per-repo git probes).
- **Errors are localized.** A failure in `P1-30` (e.g., MAS auth) does not corrupt `P1-10`'s rendered files or `P1-40`'s installed mise tools. The orchestrator collects errors and reports them at the end of the run.
- **Logging.** Every step writes its output to `~/.local/state/macbook-setup/run-<timestamp>.log` (full unbuffered output, including stderr). The colored summary on stdout is for humans; the log is for forensics.
- **`--dry-run` runs all probes and prints what would happen** without executing modifying commands. `brew bundle check` is read-only by design; `chezmoi diff` is read-only; `mise install --dry-run` exists; `git clone` is replaced with a `printf` in dry-run mode. The renderer (`P1-20`) writes to a temp file in `--dry-run` and diffs against the real target.

The contract above is what makes Phase 1 safe to re-run from Claude Code conversationally. "Just run setup again" is always a valid suggestion.

## 9. Iteration & Testing

Reuses the parent PRD §9 patterns and the Phase 0 PRD §9 testing strategy. Phase-1-specific notes:

### Test target

- **VM with a Phase-0-complete snapshot.** UTM, clean macOS Sequoia image, run Phase 0 once, snapshot. Every Phase 1 iteration restores from that snapshot. This is the high-value loop: Phase 0 is slow (~10 min to install Xcode CLT, browser logins) and Phase 1 needs to be re-run dozens of times during authoring.
- **The new MacBook itself.** Used for final validation only. Phase 0 has run once; from there, run Phase 1, observe, fix, re-run.

### Idempotency probes (what `--doctor` runs)

| Probe | Step | Command |
|---|---|---|
| chezmoi clean | `P1-10` | `chezmoi diff` returns empty |
| Brewfile current | `P1-20` | `Brewfile.tmpl` mtime ≥ `brew.yaml` mtime |
| Brew bundle satisfied | `P1-30` | `brew bundle check --file=~/.config/brew/Brewfile` |
| mise per-tool | `P1-40` | `mise current <tool>` per declared tool |
| `uv tool` per-package | `P1-40` | `uv tool list` includes each `python_tools` entry |
| Repo present | `P1-50` | per-repo: dir exists, `.git/` exists, remote URL matches |

The Phase 3 doctor will produce a single table of `[ok] / [drift] / [missing]` per item. The Phase 1 `--doctor` flag is a scaffold: it runs these probes and prints `ok` or `error`, no formatted table. Good enough for Phase 1 acceptance.

### What to specifically verify

- Re-running `setup.sh --phase 1` on a Phase-1-complete VM takes <30s and shows all `skip`.
- Standalone runs: `./scripts/steps/P1-30-brew-bundle.sh` works without the orchestrator.
- Failure isolation: artificially break `P1-30` (e.g., bad Brewfile entry); confirm `P1-40` and `P1-50` still run on the next attempt.
- `--dry-run` doesn't mutate: capture `brew list`, `mise current`, and `git status` on a representative cloned public repo before, run `--dry-run`, capture after, diff should be empty.
- Tag filtering: `--include-tag gis` adds QGIS to the rendered Brewfile and triggers installation; without it, QGIS is absent from the bundle.
- Machine filter: change `data.machine` from `personal` to `work` in `~/.config/chezmoi/chezmoi.toml`, run `setup.sh --only P1-20`, verify the rendered Brewfile flips work-only entries on/off.

## 11. Boundary with Phase 2

Several pieces sit right on the Phase 1 / Phase 2 boundary; this section is explicit about which side they fall on, so neither phase accidentally takes the other's work.

| Item | Phase 1 does | Phase 2 does |
|---|---|---|
| Work-org marketplace (work overlay clone) | **Nothing** — public `repos.yaml` does not contain work-org entries in the three-repo architecture | Clone via the work overlay's `inventory/repos-<work>.yaml` (P2-30); register as Claude Code marketplace (P2-40) |
| Personal Claude plugin (personal overlay clone) | **Nothing** — `repos-personal.yaml` is not read in Phase 1 | Clone via the personal overlay's `inventory/repos-personal.yaml` (P2-30); install as Claude Code plugin (P2-40) |
| Bitwarden CLI (`bw`) | Install the binary via Brewfile (it's in `inventory/brew.yaml`) | `bw login` + `bw unlock`; export `BW_SESSION`; render private templates |
| Private dotfiles overlay | **Nothing** — does not clone, does not apply | Clone `suTerminus/dotfiles-private`; `chezmoi apply` overlay; render private gitconfig fragments, SSH config, AWS profiles |
| Work-specific tooling (Slack, Teams, etc. via MAS or cask) | **Nothing if private-only** — public Brewfile has none of these | Render private Brewfile; `brew bundle install` it |
| AWS profiles | **Nothing** | Render `~/.config/aws/config` from private template; populate via Bitwarden |
| Touch ID for sudo | **Nothing** | (Actually Phase 3) |

The shorter version: **Phase 1 only ever reads the public dotfiles repo and `inventory/*.yaml` from it.** It never invokes `bw`, never clones anything beyond the public list, never registers plugins or marketplaces. If you find a Phase 1 step doing one of these, it belongs in Phase 2.

The Phase 2 PRD (`macbook-setup-phase2-prd.md`) is the source of truth for everything in the right column. Phase 1 should not duplicate that scope.

## 13. Open Questions

Three questions from the parent PRD §10 are answered as of this Phase 1 draft. The answers are documented here so Phase 1 implementation has them on hand and the parent PRD's question list can be slimmed (M0.T07).

### Q-PARENT-3 (resolved): Mac App Store apps via `mas`?

**Decision: include MAS entries in the Brewfile; warn-not-fail if the App Store is unauthenticated.**

`inventory/brew.yaml` may carry a `mas:` block (currently empty in the Phase 1 baseline; populated by Discovery output for work-machine apps in Phase 2). The renderer emits `mas` lines in the Brewfile. `P1-30` pre-checks `mas account` and emits a `warn` if the user isn't signed in, then runs `brew bundle install` anyway. Per-entry MAS failures bubble up as warnings.

Why warn-not-fail: requiring App Store sign-in before Phase 1 can make progress is a worse UX than a clear warning the user can act on later. Bootstrap proceeds; the user signs into the App Store and re-runs `setup.sh --only P1-30` when convenient. That's the idempotent loop working as designed.

### Q-PARENT-7 (resolved): Browser profile sync stays manual.

**Decision: browsers are installable via Brewfile (Chrome / Arc / Firefox cask entries as `inventory/brew.yaml` declares), but profile sync is the user's job.**

Profile sync mechanisms vary per browser, depend on the user's identity setup, and don't fit into a one-shot bootstrap. Phase 1 installs the binary; the user signs in. If the user wants help, that's a manual handoff in the conversation, not a Phase 1 step.

### Q-P0-3 (resolved, relocated from Phase 0): Claude Code permissions on first launch.

**Decision: Phase 0 ships a minimal `phase0/claude-settings-bootstrap.json` that's copied to `~/.claude/settings.json` during step `P0-50` (claude-code).**

The minimal settings file pre-allows the bash and read tool calls Phase 1 needs (read, write, basic bash, grep) so the very first Claude Code conversation isn't a wall of permission prompts. Phase 1 then **overwrites** that bootstrap settings file when chezmoi applies `home/dot_claude/settings.json.tmpl` (which is a Phase 2 deliverable per parent PRD §8 — the file lives in Phase 2's scope even though chezmoi's apply happens in Phase 1). For Phase 1's scope, the question is: "does Claude Code work well enough to drive Phase 1?" — the bootstrap settings file makes the answer yes.

Phase 1 implementation note: do not fight the bootstrap settings file. If a chezmoi-managed `home/dot_claude/settings.json.tmpl` exists, it takes precedence (chezmoi will overwrite). If it doesn't exist (Phase 1 only, before Phase 2 is built), the bootstrap file remains in place. Both states are valid mid-build.

### Carried into Phase 1 implementation (no decision needed yet)

- The exact prompt text in `home/.chezmoi.toml.tmpl` — wording, ordering, default values for `name` and `email` — is implementation detail, not a PRD-level decision.
- The renderer's exact diff-mode output format (for `--dry-run`). Match `chezmoi diff` style for consistency, but the specifics emerge during implementation.

These don't need answers in the PRD; they get resolved when Claude Code writes the step files on the target machine.
